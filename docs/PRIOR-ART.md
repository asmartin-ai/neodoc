# Prior art: what was tried, how it failed, what Neodoc takes from it

Research for a `.docx` replacement: one plaintext HTML file, WYSIWYG markdown
editing inline, embedded images, comments/annotations, CSS-selector CLI, markdown
and docx conversion, line-oriented diffs.

Failure claims below are sourced. Rows marked **[ok]** are successes we learned
from rather than failures. Every "lesson" is traced to a decision in
[SPEC.md](SPEC.md) in the final section.

---

## 1. Office formats — why the world is stuck with `.docx`

| What | How it failed | Lesson |
|---|---|---|
| **ECMA-376 / ISO 29500** (the `.docx` spec) | ~6,000 pages at submission, 6,546 later — one 47 MB PDF was what ISO members had to review. Google's arithmetic: ODF 867 pages vs OOXML 6,546 → "it would take 18 years… to achieve comparable levels of review". The artefact itself moved mid-ballot: the 22 Jan 2007 PDF was withdrawn ~2 Feb 2007 and replaced by re-paginated parts, so objections referenced a document that no longer existed at that URL. Still churning (5th edition, 2021). [mit.edu](https://web.mit.edu/~stevenj/www/ecma376.html) · [Wikipedia](https://en.wikipedia.org/wiki/Standardization_of_Office_Open_XML) | Keep the spec small enough to read in one sitting, and make the *reference implementation + conformance corpus* the contract, not an ISO document. |
| **ISO fast-track vote (2006–08)** | 51 approve / 18 disapprove / 18 abstain (53% vs 66.67% required); 1,027 comments → 1,600-page disposition; at the BRM only ~20% of 873 changes were discussed, the rest approved by form vote; four national bodies appealed. | Winning a standards vote is not adoption. Adoption follows the editor that writes the file by default. Neodoc's lever is not a committee, it is `neodoc new` + the browser editor. |
| **Strict vs Transitional split** | The compromise died: "in practice, pressure for backwards compatibility has meant that most new files are marked up by applications using the Transitional namespace". LibreOffice still cannot *write* Strict. Microsoft ships [MS-OI29500], a ~936-page document of "areas where the product is known to vary from or extend the specification". [LOC](https://www.loc.gov/preservation/digital/formats/fdd/fdd000400.shtml) · [TDF](https://wiki.documentfoundation.org/Support_OOXML_strict_export) | One conformance class only. If a second, laxer profile exists, that profile is what gets written and the strict one is decoration. |
| **`.docx` = ZIP of XML parts (OPC)** | Undiffable and unmergeable as shipped, and the vendor's own advice is to mutate the file first: Word stamps per-paragraph revision-save IDs that change every session — "These elements and attributes show up as changed, and obscure the differences that we're looking for"; MS publishes a `RemoveRsid` recipe. Generators bake in build timestamps — "files generated on successive builds will differ, even if the source does not". Since git cannot diff a zip, every save is a whole-binary rewrite; blame, history and merge are gone. [MS blog](https://learn.microsoft.com/en-us/archive/blogs/ericwhite/remove-rsid-attributes-and-elements-before-comparing-open-xml-documents) · [pandoc manual](https://www.pandoc.org/MANUAL.html) | **The single highest-value constraint**: one flat text file, deterministic serialization, stable IDs, zero timestamps in the diff path. |
| **RTF, PDF, ODF** | RTF is plaintext but is unreadable and Word-only for fidelity; PDF is read-only (no edit loop, and PDF/A is for archival, not authoring); ODF is the same zip+XML shape as OOXML with a manifest and the same tooling story. | A format you can only *view* or only *print* is not a document format; and "plaintext" alone is not sufficient — it must also be *semantic* and *round-trippable*. |
| **Word's "Save as Web Page"** | Word HTML export produced enormous, machine-specific markup; the feature was deprecated and removed in favour of "filtered HTML". Generators that emit HTML per document are how "HTML documents" got their reputation. | Editing richness must come from a **closed vocabulary we normalize to**, never from dumping a word processor's serialization. |

## 2. WYSIWYG on HTML — why browser HTML reached disk as garbage

| What | How it failed | Lesson |
|---|---|---|
| **`document.execCommand`** | Still marked **deprecated *and* non-standard** after 25 years with no replacement: "not implemented consistently or fully by user agents, and it is not expected that this will change in the foreseeable future." Firefox made nested `execCommand()` calls always fail (bug 1634262). [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Document/execCommand) | No editing command goes behind `execCommand`. |
| **Enter → `<p>`, `<div>` or `<br>`** | Engines never converged: IE9 `<p>`, Firefox 4 `<br _moz_dirty>`, Chrome 12 `<div>`; Gecko held out until Firefox 55. Maintainer verdict: "we have no good way around it… we have no way of distinguishing a `<br>` that was inserted because the user pressed Enter and one they deliberately inserted using Shift-Enter". [whatwg list](https://lists.whatwg.org/pipermail/whatwg-whatwg.org/2011-May/031577.html) | The block model must be *ours*, never inferred from browser tag soup. |
| **Invalid nesting from paste** | W3C Editing TF measured three outcomes for one paste: WebKit `<b>fo<span><h1>bar</h1></span>o</b>` (**invalid**), IE7 `<b>fo<h1>bar</h1>o</b>` (**invalid**), Firefox valid. WHATWG: "very easy to create unserializable DOMs". [W3C editing wiki](https://www.w3.org/community/editing/wiki/ContentEditable) | Validate at the boundary: pasted/typed content is re-derived through our parser+normalizer, and block-in-inline is unrepresentable. |
| **Invisible-space injection and per-command divergence** | Chromium: pressing SPACE between two text nodes inserts `\u00a0`, "Confirmed on both Safari and Chrome". The Guardian's Scribe project kept a file-long catalogue of divergences (`insertHTML` merges `<p>` in Chrome but not Firefox; Chrome injects `line-height` SPANs on backspace; `indent` converts `<br>`s to `<p>`s in Chrome only). [Chromium 41067523](https://issues.chromium.org/issues/41067523) · [BROWSERINCONSISTENCIES.md](https://github.com/guardian/scribe/blob/master/BROWSERINCONSISTENCIES.md) | If bytes must diff line-by-line in git, invisible characters are fatal. Canonicalization must be ours, deterministic and idempotent. |
| **WebKit "Apple-style-span"** | Bookkeeping markup WebKit added to remember styles on copy/paste: "an e-mail consisting of 3 lines of text consumed 3MB in HTML"; nested cancelling wrappers `<b><span style="font-weight:normal;">…</span></b>`; serialize-on-copy and serialize-for-`innerHTML` were two separate 250-line functions that drifted. The fix took one engineer ~2 years. [webkit.org](https://webkit.org/blog/1737/apple-style-span-is-gone/) | One visual state must have exactly one representation — no reset wrappers. Hence: no `class`, no `style`, no `span`. |
| **"Why ContentEditable is Terrible" (2014)** | The same visible word "Baggins" has ≥4 equally-valid DOM encodings; a caret before it has 3 DOM positions with different typing behaviour. Conclusion: a good WYSIWYG editor is "axiomatically inconsistent" with a good general-purpose HTML editor — "as impossible as the halting problem" — unless content is "**algebraically closed** under its edits", so a paste cannot produce a document you could not have typed. [medium.engineering](https://medium.engineering/why-contenteditable-is-terrible-122d8a40e480) | Neodoc is a *constrained document model* with a closed vocabulary, not a general HTML editor. Different-hash-per-element (e.g. style/theme as CSS classes) is why the spec is small. **[ok]** — this is the design we follow. |

## 3. Single-file HTML documents

| What | How it failed | Lesson |
|---|---|---|
| **Markdeep** | **[ok]** Still alive (1.19, 2026), but: repo is "a mirror of the private repo… I do not accept pull requests", issues disabled → no bug-report surface and clear bus-factor 1; **no editing loop** (edit raw markdown, reload); rendering depends on a *fetched* script whose default is `latest`, and the changelog shows output/CSS changes across versions — "an unchanged document renders differently later". [changelog](https://casual-effects.com/markdeep/changelog.md.html) | A document must not depend on a remotely-fetched renderer, and its rendering must be frozen in the file. Neodoc inlines its stylesheet and needs zero JS to view. |
| **TiddlyWiki** | Whole-file diff noise: "a user added two one-word tiddlers to a 2.5 MB empty wiki → 200 KB diff" (long JSON context lines, story-list and theme tiddlers); a 10 MB wiki repo reached ~1 GB before `git gc`. Upgrades are manual in-place surgery of the user's own file ("You are responsible for looking after your own data"); maintainer: "I now think it was a mistake to put this information in tiddler fields, because it involves making changes to the users own data." Not markdown-native. [talk.tiddlywiki.org](https://talk.tiddlywiki.org/t/the-philosophy-and-design-of-the-single-html-file-wiki/11210) · [upgrade doc](https://tiddlywiki.com/static/How%20to%20update%20TiddlyWiki%20to%20the%20latest%20version.html) | A file whose save writes the *interpreter* back into itself turns every save into whole-file churn and every upgrade into surgery. Keep program state **out** of the document (SPEC §1: `<script>` is a lint error). |
| **MHTML (RFC 2557)** | A serializer output, not an authoring format. Only Chromium + IE display it; Firefox's "Save as rfc 2557 MHTML" bug has been open 26 years and depends on a WONTFIX; fidelity bugs persist ("Chrome doesn't save JavaScript files in MHTML archive"). No structure, no semantics, no line-oriented source. [RFC 2557](https://www.rfc-editor.org/rfc/rfc2557) · [Bugzilla 40873](https://bugzilla.mozilla.org/show_bug.cgi?id=40873) | "Bundle everything" is orthogonal to "be a document". Self-containment must come from plaintext (data URIs / relative paths), not from a container format only one engine reads. |
| **Safari `.webarchive`** | An Apple plist only Safari reads; the UK National Archives classifies it as an aggregate and admits it "cannot yet define an identification signature". Fragile even to its own vendor: Safari 18.6 failed to open webarchives it had itself created. [PRONOM fmt/866](https://www.nationalarchives.gov.uk/PRONOM/Format/proFormatSearch.aspx?id=1670&status=detailReport&strPageToDisplay=summary) · [eclecticlight](https://eclecticlight.co/2025/11/23/last-week-on-my-mac-the-mystery-of-safaris-web-archives/) | Proprietary serialization guarantees EOL. Use HTML + UTF-8: formats with decades of independent readers. |

## 4. Markdown, plaintext and block-JSON documents

| What | How it failed | Lesson |
|---|---|---|
| **Markdown → CommonMark** | The original "does not specify the syntax unambiguously" → "implementations have diverged considerably", and "because nothing in Markdown counts as a 'syntax error', the divergence often isn't discovered right away". CommonMark fixed parsing but chose HTML as its conformance **output** instead of an AST — "it would have made sense to use an abstract representation of the syntax tree instead of HTML". Everything document-shaped (comments, metadata, annotations) stayed in flavors. [spec.commonmark.org](https://spec.commonmark.org/spec) | A format defined by *how it renders* cannot be a document model. Neodoc defines a tree + validity rules; markdown is one projection. |
| **Raw HTML inside markdown** | Hosts delete it: GFM's `tagfilter` strips `<script> <iframe> <style> <title> <textarea>`, and "GitHub.com … perform additional post-processing and sanitization"; the allowed set is still undocumented ([markup#245](https://github.com/github/markup/issues/245), open since 2012). Obsidian sanitizes HTML and refuses to parse markdown inside HTML blocks ("an intentional design choice for performance optimization"). | If half your semantics live in inline HTML, you rent them from every renderer on the path. Neodoc's file *is* the artefact — never round-trip the canonical file through markdown as the storage form. |
| **reStructuredText / Sphinx** | Strictness as adoption tax: the parser "inserts a system message" into the document tree at five levels instead of failing, so bad markup yields a doc with embedded errors. [PEP 258](https://peps.python.org/pep-0258/#error-handling) | Take markdown's no-error ergonomics plus a real structural model; when we do report problems, make them actionable, in-file and machine-readable (`neodoc lint --json`). |
| **AsciiDoc / Asciidoctor / Antora** | No formal spec for ~20 years ("we need an AsciiDoc standard that's independent from Asciidoctor"); the reference implementation was an attack surface (GitHub disabled AsciiDoc rendering in 2013, restored only after a Ruby rewrite); syntax accretion forced dialect subsets (AsciiDocDITA enforces 27 rules whose errors are constructs that "cause the conversion tooling to produce invalid DITA output"); reading required a publishing system. [docs.asciidoctor.org](https://docs.asciidoctor.org/about/history/) | Expressive syntax is a loss when reading requires a toolchain. Neodoc: valid standalone HTML5, renders with zero JS, no build. |
| **Block-JSON editors (Notion/Anytype/Blocknote)** and **CRDT rich text (Yjs/Automerge/Peritext)** | **[ok]** as products, but they store opaque JSON/binary: no line diffs, no `grep`, no review, no agent editing. Peritext's own framing is that the *canonical form* problem (what the document "is") remains open once you allow concurrent rich-text edits. | Keep the canonical form textual and the diff unit meaningful; concurrency can be handled by git + our line-oriented format. |
| **CriticMarkup** | A clean plaintext spec for comments and suggested edits, but adoption never happened because it is only a convention: renderers do not ship it, so it is invisible text. [criticmarkup.com](http://criticmarkup.com/) | Use **standard HTML** for comments and changes (`<mark data-c>`, `<ins>`, `<del>`) so every existing HTML tool sees them, and offer CriticMarkup only as an export projection. |

## 5. Tooling — what addressable document editing already does right

| What | Evidence | Lesson |
|---|---|---|
| **pandoc AST + filters** | Matching is by element type + position, not by selector; only some nodes carry an `attr` — a plain `Para` exposes just `content`, so you cannot address an arbitrary block at all. [Lua filters](https://pandoc.org/lua-filters.html) | Give **every** block an addressable identity. Neodoc: CSS selectors over the whole document + a round-trippable path in `get --json`. |
| **pandoc `--to docx`** | Style binding by *name* broke under Word localization (issue 10282); the shipped reference docx was missing documented styles (10731); output in compatibility mode dropped list formatting in Office 365 (5645). [10282](https://github.com/jgm/pandoc/issues/10282) | Name-based addressing into a vendor file is fragile — but for *export only* it is acceptable. The docx writer maps to built-in style names and nothing depends on them coming back. |
| **pandoc docx reader / `--extract-media`** | "Converting from docx format causes Pandoc to lose data" (issue 8902, open); bookmarks/fields unsupported (6781); `--extract-media` silently dropped image refs (1979); media renamed to SHA1 hashes → unstable names for diffs. | Converting *from* docx is a one-way door. Neodoc's docx support is deliberately export-only, and `neodoc import` takes markdown. |
| **python-docx** | Paragraphs/tables inside revision marks (`w:ins`/`w:del`) **do not appear** in the API; nested tables excluded; content controls unread; no search/replace after ~14 years. [docs](https://python-docx.readthedocs.io/en/latest/api/document.html) · [issue 30](https://github.com/python-openxml/python-docx/issues/30) | Tracked-change content MUST be first-class queryable — in Neodoc, `<ins>`/`<del>` are ordinary selectable elements. |
| **docxtpl / python-docx-template** | Word splits a paragraph into arbitrary runs, so `{{ tags }}` break mid-token; projects ship a `merge_runs.py` pre-pass; runs also lose leading/trailing spaces without `xml:space="preserve"`. [issue 204](https://github.com/elapouya/python-docx-template/issues/204) | **Never address text below block granularity.** Character/run offsets do not survive round trips; block + optional `--quote` substring is the addressable unit. |
| **LibreOffice headless / UNO / unoconv** | A single `soffice` takes an exclusive lock on the shared profile, so concurrent conversions hang or silently drop content unless each call passes `-env:UserInstallation`, and the call has no timeout; unoconv's README: "Unoconv is deprecated". [docling#3819](https://github.com/docling-project/docling/issues/3819) · [unoconv](https://github.com/unoconv/unoconv) | A CLI is a process contract: isolated state per invocation, bounded time, deterministic exit codes. Neodoc is pure computation in-process — no third-party binary, no lock, no server. |

## 6. htmx — lessons from a hypermedia library

htmx's stated principles: **Locality of Behaviour** ("the behaviour of a unit of code should be as obvious as possible by looking only at that unit of code", explicitly traded against DRY) [essay](https://htmx.org/essays/locality-of-behaviour/); **HDA** = declarative HTML-embedded syntax instead of imperative scripting, and hypermedia rather than JSON over the wire [essay](https://htmx.org/essays/hypermedia-driven-applications/); **HATEOAS** [essay](https://htmx.org/essays/hateoas/); plus "why should only `<a>` and `<form>` make requests?", and the honesty of its own carve-outs.

| Observation | Evidence | Verdict for Neodoc |
|---|---|---|
| HDA is a poor fit for "many dynamic interdependencies", offline, or per-keystroke state — Google Sheets/Maps are the named non-amenable examples | [when-to-use-hypermedia](https://htmx.org/essays/when-to-use-hypermedia/) | **SKIP as architecture, ADOPT as frame.** The inline editor is exactly one of those carve-outs, so it is a scoped *island*; everything else about Neodoc is a plain static document. |
| Attribute inheritance was the most-criticised feature *by its own docs*: "as the attributes get further away elements, you lose Locality of Behavior" — so htmx added a config to disable it and flipped the default in htmx 4; an outside critique calls it "a definite mistake" | [quirks](https://htmx.org/quirks/#attribute-inheritance) · [chrisdone.com](https://chrisdone.com/posts/htmx-critique/) | **ADOPT the principle, never the inheritance.** No behavior is inherited in a Neodoc file: `<mark data-c="c1">` means the same thing at any depth, and every `data-*` is readable at the element carrying it. |
| Hypermedia over JSON won where the server owns the markup; HATEOAS as a doctrine did not survive contact ("broadly the industry has rejected this approach") | [hateoas](https://htmx.org/essays/hateoas/) | **ADAPT the useful half**: the document you can read contains the actions you can take — a human, a script and an agent all use the same selectors and the same file. No separate API model. |
| Small dependency-free runtime, narrow surface, progressive enhancement | htmx ships ~14KB and degrades to plain HTML | **ADOPT.** Neodoc's document needs 0 bytes of JS to render; the editor is optional and dependency-free; the whole toolchain is 1 language, 0 deps, 0 build steps. |
| `idiomorph` exists because naive `innerHTML` replacement loses focus and state | [idiomorph](https://github.com/bigskysoftware/idiomorph) | **ADOPT the diagnosis.** The editor mutates the live DOM in place; it never re-renders the document per keystroke. |

## 7. Decisions traced back to the evidence

1. One flat UTF-8 text file; deterministic serialization; `fmt` idempotent; no timestamps or session IDs in the diff path. → §1 §4
2. One conformance class. `neodoc new`, the editor and `fmt` all emit the same canonical bytes. → §1
3. Closed element/attribute vocabulary; no `class`, no `style`, no `span`, no `div`. → §2
4. `<script>` is forbidden: the document is data, never code; no state in the file. → §2 §3
5. Inline stylesheet in the file: rendering is frozen, no fetched renderer, no network. → §3
6. Textual canonical form is HTML, not markdown; markdown is a projection in and out. → §4
7. Comments/changes are standard HTML (`<mark data-c>`, `<ins>`, `<del>`), CriticMarkup only on export. → §4
8. Every block is addressable by CSS selector; `get --json` returns a round-trippable path; no sub-block addressing except an explicit `--quote`. → §5
9. docx is export-only; the CLI is in-process, per-invocation, deterministic exit codes. → §5
10. The editor is an island: no inherited behaviour, no per-keystroke re-render, no `execCommand`, and it saves through the same `format()` the CLI uses. → §2 §6
